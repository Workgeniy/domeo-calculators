# По каким тегам это парсится

Короткий ответ: **по HTML-тегам — никак.** Разметка не является источником данных.

## Почему DOM бесполезен

calcal.ru — Next.js 15 (App Router, Turbopack), React-компоненты с Tailwind. Что это значит
на практике:

- **У инпутов нет ни `name`, ни `id`, ни `data-*`.** Единственный «идентификатор» —
  простыня utility-классов вида
  `w-full px-4 py-3 rounded-2xl bg-white/80 border border-slate-200 ...`.
  Цепляться за них нельзя: классы меняются при любой правке вёрстки.
- **Варианты выбора — это `<button>`, а не `<select>/<option>`.** Тип помещения, цвет стен,
  тип лампы, ценовой уровень — всё кнопки. Активная отличается только классами
  (`bg-amber-50 border-amber-400`), значение нигде в атрибутах не лежит.
- **Формы нет.** Ни одного `<form>`, ни одного `action`. Сабмита не существует.
- **API нет.** Ни одного запроса при расчёте — ни XHR, ни fetch. Считать «дёргая эндпоинт»
  не получится, эндпоинта не существует.
- SSR-разметка содержит только результат для значений по умолчанию — 18 м², 2.7 м, LED и т.д.

Итого: скрейпинг DOM дал бы нам подписи полей и одну строку результата. Ни таблиц
коэффициентов, ни формул.

## Где на самом деле лежат данные

Всё — в постраничном JS-чанке. Схема стабильная:

1. Тянем HTML страницы.
2. Достаём `src` всех `<script>` из `/_next/static/chunks/`.
3. Отбрасываем общие чанки — те, что одинаковы на обеих страницах
   (`618aa84bdcb0169e`, `6bbcbe3dfe904bcb`, `833e2f0e336bbfd7`, `961311cbebbffb6d`,
   `a634ec5f44a38628`, `a6dad97d9634a72d`, `d598f1f652e2d146`, `d96012bcfc98706a`,
   `f83afcc2e867e657`, `turbopack-*`) — это фреймворк и общий layout.
4. Остаётся ровно **один уникальный чанк на страницу** — в нём и компонент, и справочники,
   и формула:
   - освещённость → `387cb267058b45ea.js`
   - розетки → `224b6a5bed7a0453.js`
5. Внутри чанка ориентируемся не на теги, а на **якоря в минифицированном коде**:
   - справочники — объектные литералы с кириллическими `name`/`label` и числовыми полями
     (`lux`, `coeff`, `efficiency`, `outletsMin`, `outlet`, `frame1`);
   - формула — тело `useMemo` (освещённость) или `useEffect` (розетки), где эти справочники
     используются;
   - дефолты — цепочка `useState(...)` прямо перед расчётом;
   - подписи и диапазоны полей — JSX `("input",{type:"number",min:...,max:...,value:X})`
     рядом с `children:"<подпись>"`.

## Насколько это хрупко

Имена чанков — хеши содержимого. **Любая правка калькулятора меняет имя файла**, поэтому
хардкодить хеш нельзя: его нужно каждый раз брать из HTML. Имена минифицированных переменных
(`e`, `o`, `c`, `m`, `x`, `g`, `b`, `v`) тоже пересобираются и опорой служить не могут.

Устойчивые якоря — только кириллические строки и имена полей данных: они приходят из
исходников и при переминификации выживают.

Практический вывод: это **разовое извлечение с последующей ручной сверкой**, а не
автопарсер на регламенте. Пытаться поддерживать живой парсер против хешированных бандлов —
заведомо проигрышная возня. Данных мало (два десятка констант на калькулятор), они
статичны, и в код их надо занести один раз.
